# Reading practice pilot

## Purpose

Check whether candidates can start a reading, understand the feedback, and use one suggestion in a second reading. This is a usability pilot, not evidence that the application improves interview performance.

## Suggested pilot

Recruit five willing candidates across at least two learning domains, including two who use a phone. Run one observed 20-minute session each, followed by an optional independent practice session the next day. These are proposed pilot parameters, not a statistical sample or an established benchmark. Recruitment and scheduling are handled by the team; no invitations have been sent.

Use participant codes in notes rather than names. Explain that the application sends recordings for analysis, saves reports, and currently provides audio replay only within the session. Obtain permission before any separate screen or session recording; observer notes alone are sufficient.

Before starting, verify the intended domain, available passages and candidate access. Use real candidate permissions rather than the development admin bypass. Do not enable domain restrictions or guess assignments just to run the pilot. Existing preparation-mode access remains as configured.

## Session script

Ask the candidate to think aloud. Avoid explaining where controls are until they become stuck; record any help you provide.

| Task | What to observe |
| --- | --- |
| From home, find a short reading exercise | Do they understand the daily reading goal and find the practice action? |
| Choose one passage using search or topic filters | Do they understand Quick practice, estimated difficulty and duration? |
| Continue to the microphone check | Can they allow the microphone, leave the camera off, record a sample and play it back? |
| Start and read the passage aloud | Do they notice recording has started and understand when to press Done? |
| Review the report | Ask them to explain one feedback point in their own words. Can they distinguish reported findings from rehearsal checkboxes? |
| Rehearse a flagged word or model sentence | Can they find playback and use their own recording timeline without help? No flagged words is a valid outcome; use a sentence instead. |
| Read the same passage again | Can they name the change they intend to make, then complete and save the second recording? |
| Open the saved report from reading history | Can they find the report and distinguish saved feedback from session-only audio? |

If a save or analysis fails naturally, observe recovery and record the failure. Do not interrupt real uploads or intentionally cause failures during a participant session. Exercise forced failures separately with test fixtures.

## Review and next decision

Report actual counts with denominators (for example, 3 of 5 completed without help), not percentages that suggest precision. Separate observed behaviour from candidate opinions. Record missing data explicitly.

Fix blocked recordings, lost reports and misleading feedback before adding more features. Prioritise repeated problems and high-impact failures. If candidates understand feedback but cannot choose a next exercise, prioritise the personal revision queue. If they need explanation or accountability, prioritise editor-assigned practice. If assessments repeatedly flag correct speech, investigate assessment quality before expanding coaching.

Do not treat a higher second score as proof of learning. Compare scores only when candidate, passage/reference, locale, provider and scoring version are compatible; otherwise report that comparison is unavailable. Keep usability findings separate from pronunciation or interview-performance claims.
